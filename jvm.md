## За что отвечает _JVM_:

+ Загрузка, проверка и исполнение байт кода;
+ Улучшение производительности приложения путем превращения "горячего" байт-кода в нативные машинные инструкции посредством JIT (Just-In-Time) компилятора;
+ Управление памятью и очисткой мусора (Garbage collection).

Виртуальная машина Java (Java Virtual Machine) - это среда исполнения байт-кода - набора инструкций в формате `.class` файлов.
Виртуальная машина является независимой оболочкой исполнения кода, благодаря которой возможен её запуск на любой ОС,
без влияния ОС на выполняемую программу. 

JVM работает с 2мя типами данных:  примитивные типы (**primitive types**) и ссылочные типы (**reference types**).

**Примитивы**

Делятся на два типа:

- числовые (numeric): `byte`, `short`, `int`, `long`, `char`, `float`, `double`
- `boolean`

JVM оперирует значениями как 32-битная машина, т.е. базовой единицей вычислений выступает 32-битное слово, которому соответствуют типы `int` и `float`.

- `long` и `double` (64-битные) занимают две ячейки в массиве локальных переменных фрейма или в стеке операндов (каждая ячейка — 32 бита).
- `boolean`, `byte`, `short` и `char` на уровне вычислений трактуются как `int`: значения расширяются до 32 бит (знаковое расширение для `byte`/`short`, беззнаковое — для `char`). Для этих типов существует лишь несколько специализированных инструкций: загрузка, сохранение и преобразование типов; отдельного полноценного набора арифметических операций нет.
- `boolean` отдельного представления в байт-коде не имеет: компилятор использует `int` (0 = `false`, 1 = `true`). Массивы `boolean[]` физически хранятся как массивы `byte`.

Значения примитивных типов хранятся на стеке (stack), без использования указателей (ссылок).

**Cсылки**

Делятся на три типа:

- классы (class types): `String`, `Object`, `MyClass`, ...
- интерфейсы (interface types): `Serializable`, `Closeable`, `MyInterface`, ...
- массивы (array types): `[]int`, `[]String`, `Object[][]`, ...

Значение ссылочного типа — это ссылка (reference) на объект в куче (heap), либо специальное значение `null`, означающее отсутствие ссылки.

**Некоторые отличия на практике**

При копировании примитивных типов копируется значение, а при копировании ссылочных типов - ссылка.

```java
// the value of a is copied into b
// a and b hold independent values on the stack
int a = 1;
int b = a;

// the reference is copied
// x and y reference the same object on the heap
Object x = new Object();
Object y = x;
```

Оператор равенства `==` сравнивает значения у примивных типов и равенство ссылок (не содержимого) у ссылочных типов.

## Classloader

Загрузчик классов является частью JRE, которая динамически загружает Java классы в JVM. 
Обычно классы загружаются только по запросу. Система исполнения в Java не должна знать о файлах и файловых системах
благодаря загрузчику классов. **Делегирование является важной концепцией**, которую выполняет загрузчик. Загрузчик классов 
отвечает за поиск библиотек, чтение их содержимого и загрузку классов, содержащихся в библиотеках. 
Эта **загрузка** обычно выполняется **«по требованию»**, поскольку она не происходит до тех пор, пока программа не вызовет класс.
**Класс с именем может быть загружен только один раз данным загрузчиком классов.**

JVM имеет 3 встроенных загрузчика классов:

- Bootstrap ClassLoader
- Platform/Extension ClassLoader
- Application/System ClassLoader

Часть исходного кода, подтверждающая этот факт:

```java
package jdk.internal.loader;
...
public class ClassLoaders {
    ...
    // the built-in class loaders
    private static final BootClassLoader BOOT_LOADER;
    private static final PlatformClassLoader PLATFORM_LOADER;
    private static final AppClassLoader APP_LOADER;
    ...
}
```

Условно они делятся на 2 группы:

- Bootstrap ClassLoader - поставляется с JVM в виде нативного кода, недоступен в рантайме
- ClassLoader objects (Platform ClassLoader и Application ClassLoader)  - объекты типа java.lang.ClassLoader, JVM создает их в момент запуска

_Bootstrap ClassLoader_ написан на C/C++ и скомпилирован в нативный код под конкретную OS и архитектуру CPU. Компиляция в наивный код необходима для того, чтобы загрузить core Java classes из модуля `java.base`, необходимые для работы самой JVM (до Java 9 core классы загружались все разом из “runtime jar” - `rt.jar`, что было не оптимально). В отличие от ClassLoader objects, у него нет родительского класса и при попытке обратиться к нему возвращается `null` (Bootstrap ClassLoader - это нативный код, а не Java объект).

_ClassLoader objects_ подгружают классы динамически, в рантайме. Они являются наследниками класса `jdk.internal.loader.BuiltinClassLoader`, который, в свою очередь, наследуется от абстрактного класса `java.lang.ClassLoader` (через `java.security.SecureClassLoader`) и переопределяет (overrides) метод `protected Class<?> findClass(String name)`.

_Platform ClassLoader_ загружает модули платформы и расширений JDK, которые не являются частью модуля `java.base` (например, `java.sql`, `java.desktop`, `java.xml.crypto` и пр.). Его родительский загрузчик классов - Bootstrap ClassLoader.

Application ClassLoader загружает классы из classpath (флаг `-cp`) и module path (флаг `-p`, Java 9+), которые относятся непосредственно к нашему приложению: `.jar` и `.class` файлы, а также зависимости. Его родительский загрузчик классов - Platform ClassLoader.

```java
ClassLoader appLoader = MyClass.class.getClassLoader(); // AppClassLoader
ClassLoader extLoader = appLoader.getParent();          // PlatformClassLoader
ClassLoader bootLoader = extLoader.getParent();         // null — Bootstrap is native, no Java object
```

**Пользовательский загрузчик классов**

Загрузчик классов написан на Java. Поэтому возможно создать свой собственный загрузчик классов, не понимая тонких деталей JVM.
У каждого загрузчика классов Java есть родительский загрузчик классов, определенный при создании экземпляра нового 
загрузчика классов или в качестве системного загрузчика классов по умолчанию для виртуальной машины.

Что делает возможным следующее:
* загружать или выгружать классы во время выполнения (например, динамически загружать библиотеки во время выполнения, даже из ресурса HTTP).
Это важная особенность для:
    - реализация скриптовых языков;
    - использование bean builders;
    - добавить пользовательское расширение;
    - позволяя нескольким пространствам имен общаться. Например, это одна из основ протоколов CORBA / RMI;
* изменить способ загрузки байт-кода (например, можно использовать зашифрованный байт-код класса Java);
* модифицировать загруженный байт-код (например, для переплетения аспектов во время загрузки при использовании аспектно-ориентированного программирования);

## Области данных времени выполнения

Runtime data areas делятся на две группы:

- **общие (shared)** - общие для всех потоков:
  - _Heap_ - все объекты и массивы, управляется GC
  - _Method Area_ - метаданные классов, байткод методов, runtime constant pool, static-поля
- **потоковые (per-thread)** - своя копия на каждый поток:
  - _PC Register_ - указатель на текущую выполняемую инструкцию
  - _JVM Stack_ - стек _фреймов_ (локальные переменные, стек операндов, указатель на constant pool)
  - _Native Method Stack_ - стек вызовов нативного кода (JNI)

```shell
JVM Memory
├── Shared
│   ├── Heap
│   └── Method Area
└── Per-thread 
    ├── PC Register
    └── JVM Stack
    └── Native Method Stack
```

### Shared Data Areas 

**Heap**

Куча (heap) - это область данных рантайма, из которой выделяется память для всех объектов и массивов. Куча является общей для всех потоков, и создается при запуске виртуальной машины. За управление памятью кучи отвечает GC (Garbage Collector - сборщик мусора). Неиспользуемые объекты удаляются автоматически, без непосредственного участия разработчика. Спецификация JVM гарантирует только сам факт автоматического управления памятью, а какой именно сборщик мусора работает "под капотом" - решает конкретная реализация JVM и/или сам разработчик, запуская JVM с нужными флагами под свои требования.

Размер кучи может быть:

- _фиксированный_ - задается при старте JVM и не меняется
- _динамический_ - растёт при нехватке места под новые объекты, и сжимается, когда GC обнаруживает большое количество неиспользуемой памяти

Размер кучи устанавливается флагами:

```shell
-Xms512m    # initial size (512 Mb)
-Xmx2048m   # max size (2048 Mb)
```

- `-Xms = -Xmx` - фиксированный размер
- `-Xms < -Xmx` - динамический размер

**Method Area**

Область данных, доступная всем потокам, и хранящая:

- метаданные классов - имя, модификаторы, суперкласс, интерфейсы
- байткод методов
- Runtime Constant Pool - константы, строковые литералы, ссылки на методы/поля
- static-поля классов
- информацию для method resolution (например, [vtables](./oop.md#что-такое-статическое-и-динамическое-связывание))

Method Area - это спицификация, абстрактное понятие. Детали реализации зависят от конкретной JVM.

### Per-thread Data Areas 

**PC Register**

JVM поддерживает большое количество потоков исполнения одновременно. Каждый поток виртуальной машины Java имеет свой собственный регистр PC (Program Counter). В любой момент времени каждый поток виртуальной машины Java выполняет код одного метода - текущий метод для этого потока. Если этот метод не является native, регистр PC содержит адрес инструкции виртуальной машины Java, выполняемой в настоящее время.

Коротко говоря: для каждого потока существует один PCR, который создается при запуске потока. PCR хранит адрес выполняемой сейчас инструкции JVM.

**JVM Stack**

JVM Stack создается одновременно с потоком и хранит [фреймы](#frames) (Stack Frames) - по одному на каждый вызов метода. Стек растет снизу вверх - каждый новый фрейм добавляется наверх стека. Удаление фреймов со стека происходит в обратном порядке - сверху вниз. Такой подход называется LIFO (Last In First Out):

```shell
Called method A()  → push frame A
  A called B()     → push frame B
    B called C()   → push frame C
    C returned     → pop frame C
  B returned       → pop frame B
A returned         → pop frame A
```

Размер стека задается в момент создания потока и не менятся динамически (в отличие от кучи). Размер по умолчанию зависит от платформы и версии JVM, его можно задать:

- в момент запуска приложения с помощью флага `-Xss` (стек каждого потока будет указанного размера): 

```shell
java -Xss512k -jar app.jar   # 512 Kb (per-thread)
java -Xss1m -jar app.jar     # 1 Mb
```

- в рантайме - в момент запуска потока (стек конкретного потока будет указанного размера):

```java
Thread t = new Thread(null, runnable, "my-thread", 2 * 1024 * 1024);   // 2 MB
```

Trade-off при определении размера стека: больше потоков - меньше стек каждому, меньше потоков - больше стек каждому.

**Native Method Stack**

Аналог JVM Stack, используемый для выполнения native-кода - методов, написанных не на Java, а вызываемых через JNI (Java Native Interface). В примере ниже, когда JVM встречает вызов `computeSomething()`, выполнение уходит в native-код (C/C++), который использует отдельный стек - Native Method Stack, а не обычный JVM Stack.

```java
public class NativeExample {
    static {
        System.loadLibrary("mylib");
    }

    // native method - implemented in C/C++
    public native int computeSomething(int x);
}
```

JVM Stack оперирует байткодом (фреймами), а Native Method Stack - нативными фреймами (как это делает C/C++ на своей платформе). Разные стеки - следствие разных моделей выполнения.

## Frames

_Stack Frame_ - это единица данных в JVM Stack. Создаётся при каждом вызове метода, уничтожается при выходе из него. Frames выделяются из JVM Stack потока, создающего frame. Структура frame по спецификации:

```shell
Stack Frame
├── Local Variable Array (LVA)           // method params + local variables
├── Operand Stack                        // working area for calculations
├── Reference to Runtime Constant Pool   // used for dynamic linking
└── (additional implementation-specific data: return address, reference to caller frame, etc.)
```

Размеры массива локальных переменных и стека операндов определяются во время компиляции и предоставляются вместе с кодом для метода, связанного с фреймом.
Таким образом, размер структуры данных, frame-а зависит только от реализации виртуальной машины Java, и память для этих структур может быть выделена одновременно при вызове метода.

Только один frame активен в любой точке данного потока управления - метода выполнения, и это frame называется текущим, а его метод известен как текущий метод.
Класс, в котором определен текущий метод, является текущим классом. Операции над локальными переменными и стеком операндов обычно выполняются со ссылкой на текущий frame.

Frame перестает быть текущим, если его метод вызывает другой метод или если его метод завершается. Когда метод вызывается, новый frame создается и становится текущим, 
когда управление переходит к новому методу. При возврате метода текущий frame передает результат вызова метода, если таковой имеется, в предыдущий frame. 
Текущий frame затем отбрасывается, так как предыдущий frame становится текущим. Обратите внимание, что frame, созданный потоком, 
является локальным для этого потока и на него не может ссылаться ни один другой поток.

### Local Variable Array (LVA)

Каждый frame содержит массив ячеек (slots), пронумерованных с 0, и известный как локальные переменные фрейма (Local Variable Array - LVA). Длина LVA для frame-а определяется во время компиляции 
и поставляется в байт-коде класса или интерфейса вместе с кодом для метода, связанного с frame-ом.

1 LVA slot может хранить значение типа: boolean, byte, char, short, int, float, reference, or returnAddress. 
2 последовательных LVA slots могут хранить значение типов: long или double.

JVM использует LVA для передачи параметров при вызове метода и хранения локальных переменных метода. При вызове метода класса все параметры передаются в LVA, начиная с индекса 0. При вызове non-static метода локальная переменная 0 всегда используется для передачи ссылки на объект,для которого вызывается метод экземпляра (`this` в Java). Последующие параметры начинаются с индекса 1.

```java
void method(int a, long b) {
    int c = a + 1;
}

slot 0:   this  // (for non-static methods)
slot 1:   a     // (int takes 1 slot)
slot 2-3: b     // (long takes 2 slots)
slot 4:   c
```

### Operand Stack

Каждый frame содержит стек «последний вошел - первый вышел» (LIFO), известный как стек операндов. Максимальная глубина стека операндов frame-a
определяется во время компиляции и предоставляется вместе с кодом для метода, связанного с frame-ом.

Стек операнда пуст при создании frame-a, который его содержит. JVM предоставляет инструкции для загрузки констант 
или значений из локальных переменных или полей в стек операндов. Другие инструкции JVM берут операнды из стека операндов, 
оперируют с ними и помещают результат обратно в стек операндов. Стек операндов также используется для подготовки параметров 
для передачи в методы и для получения результатов метода.

Для примера, инструкция **iadd**  суммирует два int-вых значения. От стека операндов требуется, чтобы два int-вых значения были наверху стека.
Значения удаляются из стека, операция **pop**. Суммируются и их сумма помещается в стек операндов.

### Reference to Runtime Constant Pool

Каждый метод в Frame принадлежит конкретному классу, и у каждого класса есть свой Runtime Constant Pool, который хранится в Method Area. Во избежание копирования данных, Frame хранит ссылку на участок памяти Method Area того класса, которому принадлежит текущий выполняемый метод.

Ссылка на Runtime Constant Pool нужна для dynamic linking: байт-код _не хранит прямых адресов памяти, только символические ссылки_, которые резолвятся через ссылку на Runtime Constant Pool. Байт-код _компилируется с символическими ссылками, а не реальными адресами_, потому что на момент компиляции реальные адреса в памяти ещё не известны (классы будут загружены JVM позже, возможно из других jar и classloader-ов).

Содержимое Runtime Constan Pool:

- Строковые литералы
- Числовые константы
- Символические ссылки на классы
- Символические ссылки на методы
- Символические ссылки на поля

### Нормальный выход из фрейма

Frame корректно завершается и передаёт значение (если есть) в Frame вызывающего через `return`.

**Алгоритм**

1. Выполняется return-инструкция в текущем Frame
2. Если есть значение - оно берётся с ВЕРШИНЫ Operand Stack текущего Frame
3. Текущий Frame уничтожается (pop из JVM Stack)
4. Значение (если было) кладётся на Operand Stack Frame'а ВЫЗЫВАЮЩЕГО метода
5. PC вызывающего восстанавливается на инструкцию СЛЕДУЮЩУЮ после call
6. Выполнение продолжается в Frame вызывающего

### Выход из фрейма при исключении

Вместо передачи значения через `return`, запускается механизм _раскрутки стека_ (stack unwinding) с поиском обработчика исключения.

Каждый фрейм имеет _таблицу исключений_ (exception table), сгенерированную компилятором для try-catch блоков. Порядок записей в таблице соответствует порядку блоков `catch` в исходном коде, поэтому более специфичный `catch` должен идти раньше общего.

```java
void method() {
    try {
        risky();
    } catch (IOException e) {
        handleIO(e);
    } catch (RuntimeException e) {
       handleRuntime(e);
   }
}

Exception table:
  start_pc    end_pc    handler_pc   catch_type
  0           5         8            IOException
  0           5         15           RuntimeException
```

- `start_pc`/`end_pc`

Границы защищенного региона байт-кода (блок `try`) в байтах, смещение от начала метода, _не включая_ `end_pc`. В примере выше защищенная зона [0; 5), в нее входят инструкции 0, 1, 2, 3, 4.

- `handler_pc`

Смещение байткода, на которое передаётся управление, если исключение попало в диапазон `[start_pc, end_pc)` и тип совпал с `catch_type`. Это адрес начала блока `catch`. В примере выше два блока `catch` и два соответствующих им значения `handler_pc`.

- `catch_type`

Ссылка на constant pool — конкретный класс исключения, который перехватывает эта запись.

**Алгоритм stack unwinding при выбросе исключения**

1. Исключение выброшено в текущем Frame
2. JVM ищет в exception table ТЕКУЩЕГО Frame подходящий handler:
  - нашли - передать управление на target, Frame НЕ уничтожается
  - не нашли - Frame уничтожается (unwind), поднимаемся к вызывающему Frame
3. Повторить шаг 2 в Frame вызывающего
4. ... пока не найдётся handler или не закончится стек
5. Если стек закончился - поток завершается (или дальше по UncaughtExceptionHandler)

**Алгоритм поиска подходящей записи в exception table**

1. Пройти таблицу СВЕРХУ ВНИЗ (порядок важен!)
2. Первая запись, где:
   - PC инструкции-виновника ∈ [start_pc, end_pc)
   - выброшенное исключение instanceof catch_type
3. Совпало - jump на handler_pc
4. Ни одна не подошла - unwind текущего Frame

**Пример stack unwinding**

```java
void a() { b(); }
void b() { c(); }
void c() { throw new RuntimeException(); }

void main() {
    try {
        a();
    } catch (RuntimeException e) {}
}

Frame[c] - no handler - unwind
Frame[b] - no handler - unwind
Frame[a] - no handler'а - unwind
Frame[main] - HAS handler - stop here
```

Компилятор дублирует байт-код блока `finally` в каждую точку выхода (return, exception, normal flow), он исполняется перед каждым уничтожением (unwind) фрейма.

```java
void method() {
    try {
        throw new RuntimeException();
    } finally {
        cleanup();   // executes befure unwinding the current Frame
    }
}
```

## Execution Engine

Байт-код, назначенный **run-time data areas**, будет выполнен **execution engine**. Механизм выполнения считывает байт-код и выполняет его по частям.

**Interpreter**

Интерпретатор интерпретирует байт-код быстро, но выполняется медленно. Недостаток интерпретатора заключается в том, что, когда один метод вызывается несколько раз, каждый раз требуется новая интерпретация.

**JIT Compiler**

JIT-компилятор устраняет недостатки интерпретатора. Механизм выполнения будет использовать помощь интерпретатора при преобразовании байт-кода, 
но когда он находит повторный код, он использует JIT-компилятор, который компилирует весь байт-код и изменяет его на собственный код. 
Этот нативный код будет использоваться непосредственно для повторных вызовов методов, которые улучшают производительность системы.

+ Генератор промежуточного кода (Intermediate Code Generator). Производит промежуточный код.
+ Code Optimizer. Отвечает за оптимизацию промежуточного кода, сгенерированного выше.
+ Генератор целевого кода (Target Code Generator). Отвечает за генерацию машинного кода или родной код.
+ Профилировщик (Profiler). Специальный компонент, отвечающий за поиск горячих точек, то есть, вызывается ли метод несколько раз или нет.
